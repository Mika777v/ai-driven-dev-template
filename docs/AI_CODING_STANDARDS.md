# AI_CODING_STANDARDS — コードの書き方

> **目的**: AI が書くコードの品質の下限をそろえる。言語に依存しない原則（§1〜§6）と、プロジェクト固有の決まり（§7）に分ける。リンターや型チェックで機械的に守れるものは**ツールに任せ**、ここには「ツールでは守れない判断」を書く。
> **いつ読むか**: コードを書き始める前（初回）。レビューで指摘されたとき。新しい種類のコード（初めての層・言語）を書くとき。
> **差し替え**: §1〜§6 はそのまま使える。§7 をプロジェクトの言語・フレームワークに合わせて埋める。合わない原則は消してよい。末尾の「記載例」は消してよい。

---

## 1. 最優先: 既存のコードにそろえる

- 書く前に、**同じ種類の既存のコード**を探して、名前の付け方・エラーの扱い・ファイルの置き方をまねる
- ルールとここが食い違うときは、既存のコードの書き方を優先し、食い違いを報告する（このファイルを直す PR を提案する）
- 新しいライブラリ・新しい書き方を持ち込むときは、理由を PR に書く

## 2. 変更の大きさ

- 頼まれたことだけを変える。ついでのリファクタリング・整形・名前の変更をしない（差分が読めなくなる）
- 整形ツールが決まっていないときは、触った行以外を整形しない
- 1つの PR は1つの目的。目的が2つあれば PR を分ける

## 3. 設計

- **純粋な計算と、外とのやりとり（DB・API・ファイル・時刻・乱数）を分ける。** 計算は関数にしてテストを書く
- **入力の検証は境界（API の受け口・画面のフォーム・ファイルの読み込み）で1回だけ行う。** 内側では検証済みの型を信じる
- 同じルール（判定・定数・表示の文字）を2か所に書かない。やむを得ず2か所になるときは、互いの場所をコメントに書く
- 将来のための抽象化は、2つ目の使い道が出てから作る
- 外部サービスはインターフェースの後ろに置き、テストでは差し替える

## 4. エラーと境界

- エラーを握りつぶさない（空の catch・無視した戻り値を作らない）。扱えないなら上に返す
- 利用者に見せるメッセージと、ログに残す詳しい情報を分ける
- 日付・時刻・タイムゾーン・通貨・文字コードは、プロジェクトで1つの扱い方に決める（§7）

## 5. テスト

- ロジックを変えたら、テストを追加か更新する。バグを直したら、そのバグを再現するテストを先に書く
- テストは「何を確かめたいか」が名前でわかるようにする
- **テストを消す・飛ばす・期待値を実装に合わせて書き換えて、CI を通さない。** テストが間違っていると思ったら、理由を PR に書く
- 外部のネットワークに依存するテストは、既定では動かさない

## 6. セキュリティと依存

- 秘密情報は環境変数か秘密の管理の仕組みから読む。コード・テスト・ログ・例に本物の値を書かない（`.env.example` には形だけ）
- 外から来た文字列を、SQL・シェル・HTML にそのまま埋め込まない（プレースホルダ・エスケープを使う）
- 依存ライブラリを入れる・上げるときは:
  - **公開から {{DEPENDENCY_COOLDOWN_DAYS}} 日以上たった版**を選ぶ（出たばかりの版は、壊れていたり乗っ取られていたりすることがある）
  - 保守が続いているか（最近のリリース・issue への反応）を確かめる
  - 標準ライブラリや既にある依存で済むなら入れない
- GitHub Actions のサードパーティの Action は、**コミットのハッシュで固定**する（タグは書き換えられる）

## 7. このプロジェクトの決まり

| 項目 | 決まり |
|---|---|
| 言語・バージョン | {{LANGUAGE_VERSION}} |
| 整形・lint | {{FORMATTER_LINTER}}（例: Prettier は入れていない / ruff を使う） |
| 型 | {{TYPE_RULES}}（例: `any` を使わない。外からの値は `unknown` で受けて絞る） |
| 命名 | {{NAMING}}（例: ファイルは kebab-case、型は PascalCase） |
| ディレクトリの責務 | {{LAYERING}}（例: `shared/` は他に依存しない） |
| エラーの形 | {{ERROR_SHAPE}}（例: API は `{ fieldErrors: { name: "..." } }` を返す） |
| 日付・時刻 | {{DATETIME_RULE}}（例: 日付は `YYYY-MM-DD` の文字列） |
| コメント | {{COMMENT_RULE}}（例: 「なぜ」だけ書く。「何を」はコードで表す） |
| テストの置き場所 | {{TEST_LOCATION}} |

### 7.1 学習・解説（任意）

<!-- 学習を兼ねるプロジェクトだけ残す -->
- 実装の PR には、その PR で使った言語特有の書き方の解説を `{{LEARNING_DIR}}` に1つ足す（ファイル名 `YYYY-MM-DD-内容.md`）
- 書くこと: 何をしたか（2〜3行）→ 実際のコード → なぜそう書くのか・他の言語とのちがい・はまりやすい所 → 手元で確かめる方法

## 記載例

<details>
<summary>例: TypeScript（React + Node.js）の §7</summary>

```markdown
| 言語・バージョン | TypeScript 5 系、Node.js は `.nvmrc` の版 |
| 整形・lint | ESLint だけ。整形ツールは入れていない（幅 120 くらいで手で整える） |
| 型 | `any` を使わない。API の入力は `unknown` で受け、型ガードで絞る |
| ディレクトリの責務 | `shared/` は frontend・backend のどちらにも依存しない |
| エラーの形 | 入力エラーは 400 + `{ fieldErrors }`。画面では判定せず、欄ごとに表示する |
| 日付・時刻 | 日付は `YYYY-MM-DD` の文字列。`Date` は境界でだけ使う |
| テストの置き場所 | 対象と同じフォルダに `*.test.ts` |
```

</details>

<summary>例: Java（Spring Boot）の §7</summary>

```markdown
| 言語・バージョン | Java 21（LTS に固定）、Spring Boot 4 |
| ディレクトリの責務 | Spring Modulith のモジュール境界を守る（`./gradlew build` で検査） |
| 命名 | API の DTO の record 名はモジュールをまたいで重ねない（OpenAPI のスキーマ名が衝突する） |
| エラーの形 | `ApiErrors` で RFC 9457 の Problem Details を返す |
| テスト | DB を使うテストは Testcontainers。テストのユーザーは users テーブルに実際に登録する |
```

</details>
