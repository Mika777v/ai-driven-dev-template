# AI_PROJECT_CONTEXT — プロジェクトの前提

> **目的**: AI が「何を・誰のために・どこまで作るか」を取り違えないための、プロジェクト固有の前提をまとめる。コードを読んでもわからない**意図・制約・やらないこと**を書く場所。
> **いつ読むか**: 新しいセッションの最初（`AGENTS.md` の次）。機能を設計するとき。スコープの内か外か迷ったとき。
> **差し替え**: このファイルは**ほぼ全部がプロジェクトごとに書き換える部分**。`{{...}}` を埋め、使わない節は消す。末尾の「記載例」は書き終えたら消してよい。
> **書き方のコツ**: 文章より箇条書き・表。1項目1行。「なぜ」を短く添える（AI は理由があると、書かれていない場面でも正しく判断できる）。

<summary>例: 経費精算アプリ（個人開発・学習を兼ねる）</summary>

```markdown
## 1. 概要
- **プロダクト名**: routepense
- **一言で**: 出勤ルートを登録し、日ごとに在宅/出勤を選んで期間をまとめて登録できる経費精算アプリ
- **解決したい課題**: 毎月の交通費精算で、同じルートを日ごとに入れ直す手間
- **対象の利用者**: 自分（個人利用から始める）
- **目的の種類**: 実用 + TypeScript の学習
- **開発体制**: 1人 + AI

## 2. 技術スタック
| 言語 | TypeScript（フロント・バック共通） | 型をフロントとバックで共有できる |
| データ保存 | SQLite | 開発が手軽。後で差し替えやすい構成にする |

## 3. 作る機能
| F1 | 出勤ルートの登録・一覧・削除 | Must | 完了 |
| F2 | 期間を指定した一括登録 | Must | 進行中 |
| F3 | 月ごとの一覧と交通費の合計 | Must | 未着手 |

## 4. やらないこと
- 承認フロー、複数ユーザー、認証
- 経路探索による運賃の自動計算
- PDF 出力

## 5. 設計の方針
- 勤務区分は判別可能なユニオン型（`{ kind: "remote" } | { kind: "commute"; routeId: string }`）
- 日付は文字列（YYYY-MM-DD）で扱い、タイムゾーンのずれを避ける
- 一括登録のロジックは純粋関数にしてテストを書く
- バリデーションは入力の境界（API の受け口）で行う

## 8. 用語集
| 勤務区分 | その日が在宅か出勤か | `WorkKind` |
| 当てはめ | 一括設定を保存前に画面へ反映すること | `Draft` |
```

</details>

<details>
<summary>例: 社内規程の検索ナビ（ポートフォリオ・小規模チーム想定）</summary>

```markdown
## 1. 概要
- **一言で**: 「何を調べればいいかわからない」を「誰に・何を・どこで」まで案内する社内規程ナビ
- **目的の種類**: ポートフォリオ（架空企業のダミーデータだけを使う）

## 4. やらないこと
- 実在の企業・規程・人物・連絡先を入れること
- MVP での AI（LLM）機能。検索だけで成立させてから段階的に足す

## 5. 設計の方針
- 権限は検索の前に SQL で絞る。件数からも見えないものを漏らさない（ADR-0004）
- 窓口・根拠は構造化データから描画し、LLM には説明文だけを書かせる

## 6. 制約
| セキュリティ | 公開範囲の判定は backend の `AccessPolicy` の1か所に置く |
```

</details>
