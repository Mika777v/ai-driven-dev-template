# AI_WORKFLOW — 作業の進め方（Issue → PR → 報告）

> **目的**: AI に「何を、どの単位で、どこまで進めて、いつ止まるか」を決めておく。止めずに進めてよい作業と、人の判断を待つ作業を分けることで、人の確認の手間を減らしつつ、戻しにくい変更だけは人が見る。
> **いつ読むか**: 次にやる作業を選ぶとき。Issue を作る・閉じるとき。区切りの報告を書くとき。
> **差し替え**: `{{...}}` の箇所（区切りの単位・Issue の種類・ラベル）をプロジェクトに合わせる。流れ自体はそのまま使える。末尾の「記載例」は消してよい。

---

## 1. 全体の流れ

```
AI_PROJECT_CONTEXT（何を作るか）
   └─ Epic（1ステップ = 1 Epic）
        └─ Task（1 PR で終わる作業。Epic の sub-issue）
             └─ ブランチ → コミット → PR（Closes #Task）→ CI → マージ
                                                    └─ Epic の Task が全部閉じたら → 区切りの報告
```

- **何を作るかの正本は `docs/AI_PROJECT_CONTEXT.md`（と要件の文書）。** Issue は「作業の単位」と「進み具合の記録」として使う
- 次にやることは、開いている Task から選ぶ。無ければ `docs/PROGRESS.md` の「次にやること」から Task を作る

## 2. Issue の種類

テンプレートは `.github/ISSUE_TEMPLATE/`、ラベルは `.github/labels.yml`。

| 種類 | 単位 | タイトルの形 | ラベル |
|---|---|---|---|
| Epic | マイルストーンの1ステップ | `[Epic] E<番号> 内容` | `type:epic` |
| Task | 1つの PR（ときに2つ）で終わる作業 | `[Task] E<番号>-T<番号> 内容` | `type:task` |
| Bug | 不具合 | `[Bug] 内容` | `type:bug` |
| Spike | 技術検証（時間を区切る。コードはマージしない） | `[Spike] 判断したい問い` | `type:spike` |

- Task は親の Epic の **sub-issue** にする（GitHub の Epic の画面で進み具合が見える）
- 戻しにくい作業（§5 の「確認が必要な項目」）を含む Issue には `needs-confirm` を付ける
- 人の作業待ち（申し込み・キーの発行など）は `blocked` を付け、何を待っているかを本文に書く

## 3. 1つの Task の進め方

1. **読む**: Task の本文 → 関係する `AI_PROJECT_CONTEXT` の節 → 触るコードの周り（全体は読まない）
2. **計画する**: 変更するファイルと確かめ方を、短く Task のコメントか PR の本文に書く。迷う設計判断があれば、作る前に聞くか ADR にする
   - 迷わなくても、**後から変えにくいこと**（DB の作り直し・データの移し方・方式や外部サービスの選択・API の形）を決めたら ADR を書く。PR の本文の「自分で決めたこと」は、マージするとコミットのメッセージに埋もれて探しにくくなる
3. **作る**: テストを先に書けるものは先に書く。1つの PR は差分 {{MAX_DIFF_LINES}} 行くらいまで（生成物を除く）
4. **確かめる**: `{{CHECK_COMMAND}}` を通す。画面や API は実際に動かして見る
   - 画面のメッセージ・API のエラー・起動のログを足す・変えたら、`docs/TROUBLESHOOTING.md` の該当の行も直す
   - Bug は、直す前に `tools/errnav/bin/errnav repro --expect '<エラーの一部>' -- <コマンド>` で再現することを確かめ、直した後に同じコマンドで再現しなくなったこと（終了コード 1）を PR の「確かめたこと」に書く
5. **PR を出す**: 本文に `Closes #Task番号`。Task が無い小さな作業は `Part of #Epic番号`
6. **マージ**: 自動マージに任せる。§5 に当てはまるときは止めて確認を待つ
7. **閉じる**: Epic のチェックリストに PR 番号を書き添える

## 4. 止めずに進めてよいこと

- 1件ずつ承認を待たずに、PR を作り続ける（CI が守りになる）
- 前の PR に依存する作業は、そのマージを確かめてから始める。待つ間は依存しない作業を進める
- 同時に開いている PR どうしで、同じファイルの同じ箇所を触らない
- 作業中に見つけた別の作業は、その場で直さず Task にして Epic に結び付ける（PR を小さく保つ）

## 5. 止まって人に確認すること

次のどれかに当てはまる PR は、自動マージせず、PR 本文の「確認が必要な項目」に書いて待つ。理由は「戻しにくい」「人が決めること」「安全に関わる」のどれか。

**確認待ちの PR があっても作業は止めない。** その PR に依存しない Task を先に進め、確認待ちの PR は区切りの報告（§6）にまとめて伝える。急ぎで判断が要るときだけ、その場で聞く。

| 項目 | 理由 |
|---|---|
| ADR の追加・変更 | 後から変えにくい判断。本文に選択肢と決めた理由を短くまとめる |
| DB のスキーマの変更・マイグレーション | すでにあるデータに影響し、戻しにくい |
| 要件・スコープの変更（`AI_PROJECT_CONTEXT.md` など） | 何を作るかは人が決める |
| 業務の決まり（何ができて何ができないか）を足す・変える | 要件の文書を直さなくても、何を作るかを決めたことになる。直したファイルではなく、決まりを決めたかどうかで見る |
| 運用ルール・CI・リポジトリ設定（`AGENTS.md`・`docs/AI_*.md`・`.github/`） | 自動マージの仕組みそのものを変える |
| 依存ライブラリのメジャーバージョンの更新 | 動きが変わりやすい |
| 認証・権限・秘密情報の扱い | 安全に関わる |
| タグ・リリース・外部への公開・お金のかかる操作 | 外に出たら戻せない |

## 6. 区切りの報告

区切りの単位: **{{CHECKPOINT_UNIT}}**（例: Epic 1つ / マージ 10〜20 件 / リリース1つ）。区切りに来たら止まり、次の形で報告する。

```markdown
## 区切りの報告: <Epic 名>

### マージした PR
- [#12](URL) feat(api): ○○を追加 — 要点を1行
- [#13](URL) ...

### 確認待ちの PR
- [#14](URL) ADR-0003 ○○ — 決めてほしいこと: A か B か（おすすめ: A。理由）

### 確かめたこと / 確かめられなかったこと
- 確かめた: `{{CHECK_COMMAND}}` が通る、画面で○○が表示される
- 確かめられなかった: ○○（理由: 環境から外部 API に届かない）

### 動作確認の方法
1. `{{RUN_COMMAND}}`
2. ○○の画面で△△する

### 次にやること
1. ...

### 次のセッションの最初の文
（AI_SESSION_GUIDE.md §5 の形で1つだけ）
```

## 7. Issue の手入れ

- Epic の Task が全部閉じたら、Epic を閉じて区切りの報告をする
- マージ済みなのに開いたままの Issue を見つけたら、対応した PR をコメントに書いて閉じる
- Spike の結果は ADR か Issue のコメントに残す（会話の中だけにしない）
