# errnav の設計

> **目的**: errnav の全体の構成・データの流れ・拡張のしかたを説明する。機能を足す・プラグインを書く・不具合を直すときの地図。
> **いつ読むか**: errnav を直すとき・プラグインを書くとき。使うだけなら [README.md](README.md) で足りる。

---

## 1. ねらい

PhpStorm などの IDE では、エラーのトレースの行を押すとソースのその行が開く。この「エラーからソースへすぐに着く」体験を、**IDE が無くても（端末・SSH 先・コンテナ・CI のログでも）** 使えるようにする。

| ねらい | どう実現するか |
|---|---|
| IDE に依存しない | Bash と POSIX のコマンドだけで動く。エディタは設定で選ぶ（vim・VS Code・PhpStorm など） |
| エラーの箇所にすぐ着く | ログから取り出したトレースを正規化し、**コンテナの中のパスを手元のファイルに結び付けて**、プロジェクトのコードのフレームを先に出す |
| 発生から再現の確認までを短く | `repro` で「コマンドを動かした間に増えたログ」だけを解析する。古いエラーと混ざらず、終了コードで再現したかがわかる |
| AI に渡しやすい | `context` で、トレース・ソース・最近の変更・ログを1つの Markdown にまとめる（秘密情報らしい値は伏せる） |

## 2. 全体の構成

```
                 ┌──────────────────────── bin/errnav（コマンドの振り分け）─────────────────────────┐
                 │  logs  scan  list  show  tree  open  context  repro  snippet  plugins  doctor     │
                 └──────────────────────────────────────────────────────────────────────────────────┘
                        │                         │                          │
   ┌────────────────────▼───────┐   ┌─────────────▼──────────────┐   ┌───────▼──────────────────┐
   │ lib/scan.sh                │   │ lib/view.sh                │   │ lib/context.sh            │
   │  ① ログの検出               │   │  一覧・詳細・呼び出し経路    │   │  AI 用の Markdown         │
   │  ② 抽出（parse.awk を呼ぶ）  │   │  ソースの抜粋（bat / awk）  │   │  秘密情報を伏せる          │
   │  ③ パスの解決               │   │  エディタで開く・リンク     │   │  クリップボードに写す      │
   │  ④ 同じエラーをまとめる      │   └────────────────────────────┘   └──────────────────────────┘
   └────────────┬───────────────┘                 ▲                          ▲
                │ 書く                             │ 読む                      │ 読む
                ▼                                 │                          │
   ┌──────────────────────────── キャッシュ（.errnav/cache/）────────────────────────────────────┐
   │ events.tsv  frames.tsv  groups.tsv  paths.tsv  raw/<id>.txt                                  │
   └──────────────────────────────────────────────────────────────────────────────────────────────┘
                ▲
   ┌────────────┴───────────────┐   ┌────────────────────────────┐   ┌──────────────────────────┐
   │ lib/repro.sh               │   │ lib/core.sh                │   │ plugins/*.sh              │
   │  ログの大きさを覚える        │   │  設定・色・外部コマンド      │   │  php node python java     │
   │  → コマンド → 増えた分を解析 │   │  OS の判定・プラグインの読込 │   │  go ruby（+ プロジェクト） │
   └────────────────────────────┘   └────────────────────────────┘   └──────────────────────────┘
```

| ファイル | 役割 |
|---|---|
| `bin/errnav` | 入口。共通のオプションを読み、サブコマンドに振り分ける。fzf の対話画面もここ |
| `lib/core.sh` | 設定（`.errnav/config`）・色・記号・外部コマンドの検出（fd/fdfind・bat/batcat）・OS の判定・プラグインの仕組み |
| `lib/parse.awk` | **中心の解析。** ログをエントリに区切り、エラーだけを選び、各言語のトレースを共通の形のフレームにする |
| `lib/scan.sh` | ログの検出・解析の呼び出し・パスの解決・まとめ |
| `lib/view.sh` | 表示（一覧・詳細・木）とエディタで開く処理 |
| `lib/context.sh` | AI 解析用のコンテキストと、秘密情報を伏せる処理 |
| `lib/repro.sh` | 再現の確認 |
| `plugins/*.sh` | フレームワークごとの差（ログの置き場所・前処理・ソースの置き場所・メモ） |
| `tests/run.sh` | テスト。`tests/fixtures/project` は各言語で実際に出したエラーの出力 |

## 3. データの流れ

```
ログのファイル / 標準入力 / repro で増えた分
   │
   │ プラグインの preprocess（例: JSON の1行のトレースを1フレーム1行に分ける）
   ▼
parse.awk ── エントリに区切る ── エラーを選ぶ ── フレームを読み取る ── 並びを正規化する
   │                                                                      │
   ▼                                                                      ▼
events.tsv                                                         frames.raw.tsv
   │                                                                      │
   │                                      パスの解決（scan.sh）◀───────────┘
   │                                             │
   │                                             ▼
   │                                        frames.tsv（解決したパス・プロジェクトの中か）
   │                                             │
   └──────────────── まとめ（同じメッセージ × 同じ発生箇所）─────▶ groups.tsv
```

### 3.1 エントリに区切る

ログの「1件の記録」を見つける。2つの方式を、ファイルごとに自動で選ぶ。

| 方式 | 選ぶ条件 | 区切り方 |
|---|---|---|
| エントリ | タイムスタンプ・レベルなどの「記録の始まり」の行が1つでもある | 始まりの行から、次の始まりの行の前まで（トレースの行は始まりの形をしていないので、前のエントリに入る） |
| 字下げ | 始まりの行が1つも無い（例外で止まったプログラムの出力など） | 字下げの無い行で区切る。ただし `Stack trace:`・`Caused by:`・`#0 `・Python の最後の例外の行・Go の goroutine の行などは続きとみなす |

「記録の始まり」の正規表現は `core.sh` の `ERRNAV_ENTRY_RE_DEFAULT` に、プラグインの `entry_re` と設定の `ERRNAV_ENTRY_RE` を足したもの。

### 3.2 エラーを選ぶ

1. 先頭の行のレベル（`ERROR`・`FATAL`・`"level":"error"`・`panic:` など）が重ければエラー
2. レベルが軽い（`INFO`・`DEBUG` など）ならエラーにしない（メッセージに「Exception」とあっても）
3. レベルが無ければ、先頭の行か、フレームのあるエントリのどこかが `ERRNAV_ERROR_RE` に合えばエラー

`--warn` で WARN もエラーとして扱う。

### 3.3 フレームの読み取り

1行ずつ、次の順に形を試す（最初に合ったものを使う）。

| 言語 | 形の例 |
|---|---|
| Python | `File "/app/x.py", line 10, in main` |
| PHP | `#0 /var/www/html/app/Foo.php(42): Foo->bar()`、`in /x.php on line 42` |
| Java / Kotlin | `at com.example.Foo.bar(Foo.java:42)` → `com/example/Foo.java` |
| Node.js | `at load (/srv/app/src/app.js:3:12)`、`at /srv/app/x.js:3:12` |
| Ruby | `from /app/lib/x.rb:5:in 'run'` |
| Go | `<TAB>/build/main.go:8 +0x18`（関数名は前の行） |
| そのほか | `/` を含む `path/to/file.ext:42`（URL の host:port は除く） |

### 3.4 並びの正規化

どの言語でも **フレーム 0 = 発生箇所（いちばん内側）、外側の呼び出しほど番号が大きい** にそろえる。

- Python は外側から書かれる（most recent call last）ので逆にする
- 例外が連鎖しているときは **根本の原因を先に**する（Java の最後の `Caused by:`・Python の最後の `Traceback`）

### 3.5 パスの解決

ログのパスは、コンテナの中（`/var/www/html/...`）やビルドしたマシン（`/home/ci/build/...`）のものであることが多い。次の順に、手元のファイルに結び付ける。

1. 設定とプラグインのパスの対応（`ERRNAV_PATH_MAP="/var/www/html=."`）
2. そのままのパスにファイルがある
3. ソースの置き場所の下にある（Java の `src/main/java` など。プラグインの `src_roots`）
4. 前から1段ずつ削って、プロジェクトの下にある（`/var/www/html/app/Foo.php` → `app/Foo.php`）
5. ディレクトリ付きの末尾で探し、1件に決まる

解決できたパスのうち `ERRNAV_VENDOR_RE`（`vendor/`・`node_modules/`・`site-packages/` など）に当たらないものを「プロジェクトのコード」とする。一覧の発生箇所は、プロジェクトのコードの最初のフレーム。

### 3.6 まとめ

「メッセージ（数字を N に置き換えたもの）」と「発生箇所」が同じイベントを1つにまとめ、件数を数える。一覧の番号は、そのまとまりの最新のイベントの番号。

## 4. キャッシュの形

すべてタブ区切り。`<ROOT>/.errnav/cache/`（`ERRNAV_CACHE_DIR` で変えられる）。

| ファイル | 列 |
|---|---|
| `events.tsv` | id・ログ・行番号・時刻・レベル・要約・先頭の行・根本の原因 |
| `frames.tsv` | id・フレームの番号・元のパス・行・関数・解決したパス・プロジェクトの中か（1/0） |
| `groups.tsv` | 最新の id・件数・レベル・時刻・要約・発生箇所・ログ・最初の id |
| `paths.tsv` | 元のパス・解決したパス・プロジェクトの中か |
| `raw/<id>.txt` | そのイベントのログの全文 |

ほかのツール（AI・スクリプト・エディタのプラグイン）からも、このファイルを読めば同じ情報が使える。

## 5. プラグイン

フレームワークの差は、トレースの形よりも「ログの置き場所」「書き方の癖」「ソースの置き場所」に出る。そのため、共通の解析（`parse.awk`）は全部の言語の形を知っていて、プラグインはその周りの差だけを受け持つ。

| 関数 | 用途 | 例 |
|---|---|---|
| `errnav_<名前>_detect ROOT` | **必須。** このプロジェクトに当てはまるか | `composer.json` がある |
| `errnav_<名前>_logs` | ログの候補（グロブ） | `storage/logs/*.log` |
| `errnav_<名前>_entry_re` | 記録の始まりの行（ERE） | 独自のログの形 |
| `errnav_<名前>_preprocess` | 解析の前の整形（標準入力 → 標準出力） | JSON の1行のトレースを分ける |
| `errnav_<名前>_path_map` | パスの対応（`from=to`） | `/var/www/html=.` |
| `errnav_<名前>_src_roots` | ソースの置き場所 | `src/main/java` |
| `errnav_<名前>_hint` | AI 用コンテキストに足すメモ | テストの動かし方 |

置き場所は `tools/errnav/plugins/`（組み込み）と `<ROOT>/.errnav/plugins/`（プロジェクト固有）。`ERRNAV_PLUGINS="php node"` で使うものを決め打ちできる。

新しい言語のトレースの形を足すときは、`parse.awk` の `parse_frame` に形を足し、`tests/fixtures/project/logs/` に実際の出力を置いてテストを書く。

## 6. 動く環境

| 環境 | 対応 |
|---|---|
| Linux / WSL / macOS | bash 3.2 以上・POSIX の awk / sed / grep。macOS の標準の bash 3.2 と BSD のコマンドを前提に書いている |
| rg・fd・fzf・bat | **どれも無くても動く。** あれば使う（fd → find、bat → awk の行番号つき表示、fzf → 番号で指定） |
| Debian / Ubuntu の名前 | `fdfind`・`batcat` も探す |
| エディタ | `ERRNAV_OPEN_CMD`（自由な形）→ `ERRNAV_EDITOR` → `VISUAL` → `EDITOR` → nvim / vim / vi / nano |

移植性のために避けていること: 連想配列・`mapfile`・`${var,,}`・`set -u`（bash 3.2）、`sed -i`・`sed` の `I` フラグ・`readlink -f`・`stat`・`date -d`（BSD）、awk の `{n}` の繰り返しと `match()` の第3引数（mawk / BWK awk）。

awk に正規表現を渡すときは `-v` を使わず環境変数（`ENVIRON`）で渡す。`-v` の値は文字列のエスケープとして処理され、gawk では `\[` の `\` が消えて正規表現が壊れる（mawk では残るので、手元では気づきにくい。GitHub Actions の Ubuntu は gawk）。

## 7. 今後の拡張の候補

| 候補 | 内容 |
|---|---|
| `watch` | `tail -F` でログを見張り、新しいエラーが出たら知らせる |
| エディタのプラグイン | `frames.tsv` を quickfix（vim）や Problems（VS Code）に流す（`errnav open` の出力は既に `file:line` の形） |
| ソースマップ | Node.js・ブラウザのビルド後のパスを元のソースに戻す |
| Windows のパス | `C:\...` のパスを WSL のパスに直す |
| C# / Rust / Elixir | トレースの形を `parse_frame` に足す |
